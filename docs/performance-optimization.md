# Property Case Radar 排程效能優化

更新日期：2026-08-30
狀態：執行中

## 目標

- 將每日工作拆分為 `capture`、`parse`、`ingest`、`score`、`verify`、`retry`、`Discord` 七個可量測階段。
- 正常無失敗日優先減少 15–30 分鐘。
- 失敗縣市重試不得阻塞每日主工作 15–45 分鐘。
- 維持公開頁面、遵守來源網站存取控制，不以提高併發繞過 CAPTCHA 或其他防機器人機制。
- 所有本機 runtime、暫存資料及測試輸出維持在 D 槽。

## 基線

2026-08-21 至 2026-08-27 的排程輸出檔時間顯示：

| 工作 | 已觀察的擷取時間 |
| --- | ---: |
| 591 租屋 | 約 9–10 分鐘 |
| 591 售屋 | 約 25–26 分鐘 |
| 法拍／OCR | 約 28–40 分鐘 |

其他已確認的固定成本：

- 租屋狀態核對最多 `500 + 500` 筆，循序執行。
- 售屋狀態核對最多 `500 + 50` 筆，循序執行。
- 失敗縣市固定等待 15 分鐘，最多 3 輪。
- 售屋、租屋入庫及重新評分存在逐筆查詢／逐筆 flush。
- 2026-08-28 的 `591-business` 狀態核對 500 筆中有 499 筆為 `unknown`。

## 實施清單

### 第一優先

- [ ] 1. 加入 `capture`、`parse`、`ingest`、`score`、`verify`、`retry`、`Discord` 精確計時。
- [ ] 2. 將 15 分鐘失敗重試改成獨立 APScheduler `date` 工作，不阻塞每日主工作。
- [ ] 3. 狀態驗證改為一個 Chromium、4 個分頁並行，並設定每站限速。
- [ ] 4. 暫時降低 `591-business` 每日驗證上限，保留設定開關供辨識修復後恢復。
- [ ] 5. Playwright 阻擋 `image`、`media`、`font`，保留 `document`、`script`、`xhr`、`fetch` 與必要樣式。

### 第二優先

- [ ] 6. 一次預載既有物件，取消每筆重複 SELECT。
- [ ] 7. 將逐筆 flush 改為批次 flush／upsert；價格歷史與通知語意保持不變。
- [ ] 8. 一次載入 `MarketPrice` 成記憶體 map，供整批售屋評分共用。
- [ ] 9. 租屋行政區中位數每批只計算一次，不為每筆物件重查。
- [ ] 10. worker 預設由 4 漸進調到 6；只有 A/B 的失敗率與 challenge 沒有惡化才測試 8。

### 第三優先

- [ ] 11. 建立 20–50 個公開頁面的 Cloudflare Browser Run A/B 工具；不以 591 作為直接替換目標。
- [ ] 12. 比較成功率、資料完整率、p50／p95、Browser 使用量與估算費用，再決定是否導入。

## 驗收指標

每次排程至少輸出以下結構化計時：

```text
performance stage=<stage> source=<source> duration_seconds=<seconds> items=<count> status=<status>
```

A/B 與正式排程必須同時保存：

- 總 wall time 與各階段時間。
- 成功／部分成功／失敗縣市數。
- 擷取筆數與欄位完整率。
- `unknown`、CAPTCHA／challenge、HTTP 429 比例。
- p50、p95 頁面時間。
- Cloudflare 回報的 browser milliseconds 與估算費用。

## 回復策略

- 所有新併發數與驗證上限均由環境設定控制，可調回原值。
- Cloudflare A/B 預設不啟用，不影響正式排程。
- 資料庫優化必須通過既有 ingest、價格歷史、通知與狀態生命週期測試後才能啟用。
- 來源成功率或筆數明顯下降時，先降低 worker，不以增加重試掩蓋品質退化。
